hs.spoons

Module

Load, install and update Spoons - packaged, reusable pieces of configuration.

Spoons live in the Spoons directory inside your config directory. Every Spoon you load is also available on hs.spoons under its name, so hs.spoons.load("Greeter") makes hs.spoons.Greeter available to the rest of your config. That's why a Spoon can't be named after one of this module's own methods or properties.

Spoons can be installed from any GitHub repository ("owner/repo"), or from a zip file at any https:// URL. There's no central list of Spoons: you choose where each one comes from, so only install Spoons from sources you trust. Pin the version you install with ref (a GitHub tag or commit) or sha256 (for a zip URL), and nothing changes until you choose to.

Quick start

// Installs Greeter the first time this runs, then loads it, configures it and starts it
hs.spoons.use("Greeter", {
    source: "jane/hs2-spoons",
    ref: "v1.2.0",
    config: { message: "Time for a break!" },
    start: true
})

hs.spoons.load(name, options) -> Object

Load an installed Spoon by name, or a Spoon from any directory with the path option. A Spoon must contain a well-formed spoon.json (with non-empty name, author, version, and description fields) and an init.js, or loading fails with an exception. init.js is loaded through the same require() used for the rest of your config, so it can itself require() further files from within the Spoon's own directory using relative paths. On success, the Spoon is also stored on hs.spoons under its name, so other code can reach it without loading it again.

init.js must set module.exports to an object (not a function) - loading fails with an exception otherwise. Its name, author, description, and version properties are then set from spoon.json, overwriting any of the same name the Spoon's own init.js set, so that information is always present and always reflects what's on disk (a warning is logged if spoon.json's name doesn't match the Spoon's directory name). If the resulting object has an init() method, it's called automatically (with this bound to the object) before load() returns - matching Hammerspoon 1's behavior. An exception thrown from init() fails the load: nothing is stored on hs.spoons, and load() throws. Unlike init.js itself (which require() only ever evaluates once), init() runs again on every load() call for the same Spoon, since the same cached object is returned each time - write it to be safe to call more than once, or do one-time setup at init.js's top level instead.

If the object has a bindings object (its actions, keyed by name), it's given a generic bindHotkeys(mapping) before init() runs, which binds the hotkeys in mapping (e.g. { show: [["cmd", "alt"], "g"] }) to those actions, and an unbindHotkeys(actions) that unbinds them again. These replace any bindHotkeys() and unbindHotkeys() the Spoon exports itself. A Spoon without bindings keeps its own, if it has them. See the Spoons guide for the details.

path is for developing a Spoon: it loads the Spoon straight from that directory (such as a .spoon2 bundle in your own checkout of its repository), instead of from Spoons/, so reloading your config picks up your changes. Nothing is installed or copied, and a Spoon of the same name that's installed is ignored. A warning is logged each time, so a config that still points at a development copy doesn't go unnoticed.

The exception's code is ENOTINSTALLED if there's no such Spoon, ENOTFOUND if path isn't a directory, EINVALIDARG if the name can't be a Spoon's or an option is malformed, or EINVALIDSPOON if the Spoon is malformed. An exception thrown by the Spoon's own code is passed on as it is.

hs.spoons.install(name, options) -> Promise<object>

Download a Spoon and install it into the Spoons directory. It isn't loaded: call hs.spoons.load() (or use hs.spoons.use(), which does both) once it's installed.

The source is downloaded as a zip file. Its Spoons are every *.spoon2 directory at its top level or in a Spoons directory, or, if there are none, the whole archive, if it's a single Spoon. An archive that holds a single directory, as a repository's does, is looked inside.

The Promise rejects with an Error whose code says what went wrong: EINVALIDARG, ENOTFOUND (no such repository, ref, URL, or Spoon in the archive), ENETWORK, EINTEGRITY (the download didn't match sha256), EINVALIDSPOON, EEXISTS, or EIO (for anything else, such as failing to write the Spoon to disk).

hs.spoons.update(name) -> Promise<boolean>

Update an installed Spoon: download it again from where it was installed from (the same source, ref and URL), and reinstall it if its version has changed. A Spoon installed from a pinned tag, commit or versioned URL doesn't change; install the newer one with install(name, { ..., force: true }) instead.

Besides the codes install() uses, the Promise rejects with ENOTINSTALLED, ENOSOURCE for a Spoon that wasn't installed by install() (or was since replaced some other way, such as by opening a .spoon2 file), or ECANCELED if the Spoon was reinstalled while the update was downloading.

hs.spoons.updateAll() -> Promise<object[]>

Update every installed Spoon, as update() does, logging each one to the Console as it's done, and then a summary. Spoons installed from the same source share one download, and different sources are downloaded one at a time. Spoons installed some other way than by install() (such as by opening a .spoon2 file) are skipped, since there's nowhere to update them from. A Spoon that fails to update doesn't stop the others. isUpdating is true until they've all finished.

Typing hs.spoons.updateAll() into the Console is enough: the updates start straight away, and their progress is logged there. The returned Promise is for code that wants the results. It never rejects: a Spoon that couldn't be updated has a status of "failed", and an error with the code and message update() would have rejected with.

hs.spoons.use(name, options) -> Promise<Object | null>

Load and configure a Spoon in one step, installing it first if it isn't installed yet - the built-in equivalent of Hammerspoon 1's SpoonInstall:andUse().

If the Spoon is already installed, it's loaded and configured before use() returns, so hs.spoons.<name> can be used on the very next line, and nothing is downloaded. If it isn't installed and source is given, it's installed in the background (see hs.spoons.install()), then loaded and configured, and a notification says so; put anything that needs the Spoon in fn, or after the returned Promise resolves. An installed Spoon is never updated by use(): call hs.spoons.update() for that.

path loads the Spoon from a directory of your own instead, as hs.spoons.load() does, for developing a Spoon: nothing is installed, and an installed copy is ignored. It takes precedence over source, ref and sha256, which are ignored while it's given, so a config can keep its source for everyone else and add path while you work on the Spoon.

Configuration is applied after the Spoon is loaded (and its init() has run), in this order: each property of config is set on the Spoon's object, exactly as if you'd assigned it yourself, hotkeys is passed to its bindHotkeys() method, fn is called with the Spoon, and finally start() is called if start is true.

The Promise rejects with an Error with a code, as hs.spoons.install()'s does, plus ENOTINSTALLED if the Spoon isn't installed and no source was given, or the error thrown by loading or configuring the Spoon.
